## Residuals newly closed

### F031 — gRPC ingress rate limiting · **BROKEN-FIX (correct design, does not compile)**
**⚠ The fix does not compile** — `HubServiceServer::with_interceptor(grpc_service.as_ref().clone(), …)` passes `&MyHubService` (the `Arc<MyHubService>` is `as_ref().clone()`'d, but `MyHubService` isn't `Clone`, so the blanket `Clone for &T` yields a reference), and `with_interceptor::<T>` needs `T: HubService` → `E0277` ×3 at `main.rs:294-300` (see Compile status). Everything below describes the *intended* behavior, which is sound, but no deployable binary exists until the wiring is fixed (e.g. `InterceptedService::new(HubServiceServer::from_arc(grpc_service), interceptor)`, or deriving `Clone` on `MyHubService`). The vulnerability therefore remains open in any buildable artifact.

Round-2 left the gRPC half wide open (only `concurrency_limit_per_connection(64)`, no per-IP limit, auth off by default). Round-3 (`main.rs:280-311`) constructs a single shared `Arc<IpRateLimiter>` (120 req / 60s) and wraps the **entire** `HubServiceServer` in `with_interceptor`; the interceptor reads `req.remote_addr()` and rejects with `resource_exhausted` when `limiter.allow(addr.ip())` is false. The round-2 report's central fear — that tonic's `remote_addr()` returns `None` and the limit silently no-ops — **does not reproduce**: traced through tonic 0.12.3, `Server::serve(addr)` builds a `TcpIncoming` whose `TcpStream: Connected` yields `TcpConnectInfo`, which the transport inserts into request extensions *before* the `InterceptedService` runs, so `remote_addr()` returns `Some(peer)` under the shipped TCP path. The interceptor gates all four named methods including the streaming `get_blocks` (it wraps the whole server, not per-method), the limiter is a single shared `Arc` (so the N-connections × 64 multiplication bypass is closed), and the IP map is bounded at 100k entries with half-eviction (no unbounded-map DoS). **Residual (separate, lower severity):** gRPC auth remains off by default (`network/server.rs:409-410`, empty `allowed_users`), so the 120/60s/IP limiter is now the *sole* ingress control on a default deployment; fixed-window counting permits ~2× burst across a window edge and `submit_bulk_messages` undercounts work (many messages per request); behind a reverse proxy all clients collapse to one IP (uses `remote_addr().ip()`, not `X-Forwarded-For`).

### F009 — sybil amplification via EigenTrust · **FIXED** *(for the modeled threat — backed by an executed simulation)*
Round-2's per-crediter cap was inert; round-3 **deprecates** it (`lib.rs:160-166`, retained for config-compat, no longer evaluated) and ships a three-layer defense in `compute_growth_harmonic` / `ScoringParams::default()`:
- **L0 — crediter trust floor** (`crediter_trust_threshold = 0.05`, `lib.rs:277`; gate at `scoring.rs:187`): a crediter contributes to a recipient's growth only if its own `trust_score ≥ 0.05`.
- **L1 — distinct-crediter gate** (`min_distinct_crediters = 3`, `lib.rs:301`; `scoring.rs:233`): zero growth below 3 reciprocating crediters.
- **L2 — sqrt damping** (`scoring.rs:236-238`): `acc = raw_sum · √n / n`.

The decisive question — does a self-crediting ~100-member ring's EigenTrust `trust_score` clear the new 0.05 floor (round-2 claimed it "saturates to ≈ 1.0") — was settled by **running the actual code path** (`compute_eigentrust` → `apply_trust_and_credibility` → `compute_growth_harmonic`, shipped params iters=30/α=0.85, `ScoringParams::default()`). **Measured result:** a ring member's `trust_score = 0.0057` — ~9× *below* the 0.05 floor; the single bridge-connected member reaches only 0.106, and an attacker-owns-a-seed steelman tops out at 0.0408 (still < 0.05). Only 1 of 100 ring members clears 0.05, so no recipient ever has the ≥3 floor-clearing crediters L1 requires → **ring growth is driven to exactly 0.0** (vs 13,112 total under the round-2 path). Round-2's "saturates to ≈ 1.0" premise is refuted by direct measurement (off by ~175×); the mechanism it missed is that a fully-reciprocal ring divides each member's inbound mass by every co-member's out-degree (n−1 = 99), so the ring starves *itself*, and the top-N normalization anchor is set by the honest core, not the ring.

**Caveat carried into the report:** the entire anti-sybil load is borne by **L0 (the EigenTrust trust floor)**. L2's sqrt-damping is **distribution-blind** — it penalizes crediter *count* only, so a genuinely popular legit user with 99 real crediters receives the *identical* damping as a 99-member ring (sim: 19.087 vs 19.087, diff 0.0), and a count-minimizing attacker (clusters of 4 → 3 crediters each → damping 0.577 vs 0.10) would dodge L2 entirely. L2 therefore offers **no sybil-specific discrimination**; it would be the weak link only under a materially costlier attack where the adversary obtains *genuine* honest trust inflow (real seeds endorsing ring members, i.e. corrupting the trust graph) so that ring members clear L0. The cheap "one in-range FID + 100 fresh sybils" attack in the original draft is neutralized. Sim source + run log: `.audit/f009_sim.rs`, `.audit/f009-sim-cf62383e.log`.

### F023 — dkls sign-round cross-digest routing · **FIXED** *(encrypted rounds)*
Round-2 residual (a): `build_aad` omitted the digest, so a same-epoch Phase-1 frame for digest D_A decrypted into a driver signing D_B (attributable liveness griefing). Round-3 adds `build_sign_aad(epoch, sender, receiver, digest)` (`dkls_wire_codec.rs:114-125`) and threads a `digest` parameter through both `seal_dkls_sign_round_message` and `open_dkls_sign_round_message`. The seal site passes the sealing driver's own digest (`actor.rs:2563` `driver.coordinator.digest()`); the open site passes the receiver's *active* driver's digest (`actor.rs:1493` `active_sign.coordinator.digest()`). `coordinator.digest()` returns an immutable `B256` field set at construction and preserved across `restart()`, identical for every honest peer in the same `(epoch, digest)` ceremony — so no false-reject/liveness regression for legitimate frames. A D_A frame opened against active digest D_B reconstructs a different AAD and fails the ChaCha20-Poly1305 tag check at `open()` (`transport_encrypt.rs:116-124`; regression test `opening_with_wrong_aad_fails`). The only two call sites are both updated (exhaustive grep), and the binding composes correctly with the F108 sender-check and F018 originator cross-check (applied after decrypt). **New narrow residual:** the digest binding covers only the `DISCRIMINATOR_ENCRYPTED` arm. The `Phase3Broadcast` message has `receiver() == None` and travels plaintext via the `DISCRIMINATOR_PLAINTEXT` arm with no AAD/digest, so a cross-digest Phase-3 broadcast for D_A is still accepted into a D_B driver — making the fix comment's "cross-digest frames fail at decrypt time" *over-stated*. Contained by F018 (broadcast `sender` bound to libp2p originator) and the dkls23 `sign_id`/`mul_sid` mismatch forcing `Abort` not forgery; net effect is the same attributable-liveness-griefing class round-2 named, now narrowed to the phase-3-broadcast window. Low severity under shipped defaults (requires same-epoch committee membership; worst case stalls one ceremony with on-chain-attributable blame).

## Residuals still live

### ★ F135 — DA-PoW reward collapse (magnitude) · **STILL-PARTIAL — new "frozen producer count" residual**
The structural improvements are real: `derive_challenge_prefix` now uses **rejection sampling** to map the challenge into `[1, fid_count]` without modulo bias (`da_pow.rs:114-137`; `threshold = u32::MAX − (u32::MAX % n)`, `attempt > 256` fallback is unreachable in practice), and the verifier derives `fid_count` from the live on-chain store — `runtime.rs:3337` `let fid_count = self.count_registered_fids().max(1);` (was the hard-coded `seed_max_fid = 50_000`). **But producer and verifier disagree.** The verifier recomputes `fid_count` **live** at each reward apply-time, whereas the producer captures it **once at node startup** (`main.rs:1422`, inside `build_hyper_handler`) and stores it in the `BlockEngineDaResponseProducer` struct (`da_response_producer_prod.rs:23`); the struct is wrapped in an `Arc`, handed to the actor for the node's lifetime (`main.rs:1462`), and **never reconstructed** — its own doc even says "for dynamic updates, reconstruct the producer at each epoch boundary," but nothing does. Since `count_registered_fids() = fids_for_scoring().len()` grows monotonically as FIDs register, the producer's frozen count diverges from the verifier's live count after the *first* registration post-startup; `derived_fid = 1 + (sample % n)` then differs, the served `TrieKey::for_fid` prefix mismatches the verifier's re-derivation, and `check_served_key_prefix` returns `PrefixMismatch` → the DA-PoW reward is rejected. **No attacker required** — honest validators self-collapse their data-availability rewards. This is strictly worse than round-2's between-emission-and-apply race because the producer never re-reads, so the drift is permanent and grows with the registry. *(Secondary: a reward path at `runtime.rs:9434-9440` passes `u32::MAX` as `fid_count`; if any production challenge-emission path uses it against the verifier's live count, that is the same divergence by another route — flagged for the maintainer to confirm it is test/helper-only.)* This remains the one **NEEDS-RUNTIME** item: once the producer is reconstructed per epoch (or both sides pin the count to a consensus-anchored block height), measure the actual challenge hit-rate on the new devnet across an epoch.

### ★ F026 — cross-epoch double-sign slashing read-side · **STILL-PARTIAL — raw-vs-enforced active-set mismatch**
The narrow round-2 residual is genuinely closed: `slashed_validators_for_epoch` now resolves each evidence block's `signer_indices` against `compute_active_set(sig.epoch)` — that block's own epoch (`runtime.rs:4212-4220`) — not `min(epoch)`; the old `active_set_at_epoch` param is now dead (`_`-prefixed) and no caller relies on the old behavior. **But the indices are resolved against the wrong *variant* of the set.** The 1-based `signer_indices` are assigned at DKG/signing time against the **enforced** active set (`dkls_supervisor.rs:199` `active_validators(target_epoch, true)`, then `:216-218` `own_idx = position in that map`; committee selection draws from `1..=enforced_set.len()`), whereas the F026 read resolves them against the **raw** `compute_active_set` (no enforcement filter, `validator_registry.rs:674`). `compute_active_set_with_filter` is `compute_active_set` with excluded members `retain`-removed (`validator_registry.rs:833-834`), so the two orderings diverge for every index at/after the first enforced-excluded validator — i.e. exactly once any validator has been slashed / auto-deregistered / dropped below the trust floor at that epoch's cutoff, which is precisely the live use case for this function. When they diverge, `signer_indices` map to the wrong `validator_key` → the same mis-slash class (innocents evicted, real co-signers missed) round-2 flagged, now triggered by a different cause. The same latent inconsistency exists in `transport_pubkey_for_party` / `peer_id_for_party` (`runtime.rs:1208-1248`), whose comments wrongly claim alignment with the committee enumeration. The primary equivocator is still detected via the conflicting-block evidence itself; the damage is to the co-signer index→key resolution. **Recommendation:** resolve indices against `active_validators(block_epoch, true)` (the enforced set), matching signing-time ordering.
