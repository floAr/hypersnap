# `tests/c2_poc.rs` — unbalanced/unsigned transfers admitted to the verkle tree

PoC for an audit finding on PR #28 (the full writeup is in the PR conversation thread). **Verified end-to-end** on Ubuntu/WSL2 (`cargo test --test c2_poc` → 3 passed, 0 failed) against `64493318130f1ebf03a787790c59f6d4a354d414`.

## What this PoC proves

A malicious proposer can submit a `HyperTransferTx` whose Pedersen commitments **do not balance** (`Σ(in) − Σ(out) − fee·B ≠ r_diff·B_blinding`) and where the spend signature is over the wrong key. The transaction will:

1. Pass `HyperMempool::submit_transfer` (no balance check, no spend-sig check, no against-store nullifier check).
2. Pass `HyperBlockBuilder::apply_message(Transfer)` (zero validation in the apply path).
3. Be applied to the verkle tree — un-backed note commitment inserted, attacker nullifier inserted.
4. Be re-applied to the verkle tree by the importer (the importer re-runs the same builder; root-match is circular).

`TransferTx::validate()` is a documented stub that explicitly defers balance closure (`crates/hypersnap-crypto/src/tokens.rs:287-301`). The three strong validators — `verify_balance_with_blinding_diff`, `validate_against_store`, `validate_with_input_pubkeys` — exist in `hypersnap-crypto` but have **zero callers outside tests**.

## Variants demonstrated

- **Primary (balance-closure-broken):** 1 input committing to 100 atoms, 1 output committing to 10,000 atoms, 0 fee. `Σ(in) − Σ(out) − fee·B` is a nonzero Pedersen point — value is being minted.
- **Stretch (no-spend-sig):** the spend signature is generated with a fresh, random secret unrelated to the (synthetic) input note's "owner." Because `submit_transfer` and `apply_message` never call `validate_against_store` or `validate_with_input_pubkeys`, the bogus signature is never checked.
- **Negative control:** when the strong validators (`verify_balance_with_blinding_diff`, `validate_with_input_pubkeys`) are called directly on the same tx, they DO reject — proving the bug is "not wired in" rather than "wrong code".

## How to reproduce

This is a pure-additive integration test under the standard Cargo `tests/` directory. No production-code modification; the helpers it depends on (`nullifier_verkle_key_public`, `note_commitment_verkle_key_public`) are already `pub fn` at `src/hyper/builder.rs:253-260`.

### Prerequisites

The hypersnap workspace requires the standard sibling-clone of `informalsystems/malachite` (per the repo's main README):

```bash

cd malachite && git checkout 13bca14cd209d985c3adf101a02924acde8723a5 && cd ..
```

## What each test asserts

### `c2_poc_unbalanced_transfer_admitted_end_to_end`

A 1-input-100-atom / 1-output-10,000-atom / fee=0 transfer is admitted by the mempool, applied by the builder, and the importer-side rebuild produces the same root — i.e. the un-backed commitment is in the canonical state.

### `c2_poc_bogus_spend_signature_admitted`

The same shape but with a spend signature generated by an unrelated key is admitted by both mempool and builder.

### `c2_negative_control_strong_validators_reject`

When called directly, `verify_balance_with_blinding_diff` and `validate_with_input_pubkeys` correctly reject the bogus inputs — proving the bug is "the strong validators are not wired in," not "the strong validators are wrong."

## Build-environment notes (incidental to the finding)

Same workarounds as documented in `tests/c1_poc.md`:

- `RUSTFLAGS="--cap-lints allow"` — rustc 1.95.0 hits an ICE in the `lifetime_syntax` lint renderer while compiling `informalsystems-malachitebft-wal`. Pinning rustc 1.94.0 also works. Not specific to this PoC or to hypersnap.
- `CARGO_TARGET_DIR` outside the workspace — fine, except for the `pre-commit` crate's build script which panics if it can't find the workspace root. Use the default in-workspace `target/` to avoid.
